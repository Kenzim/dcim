# SFTP access to NFS storage

Clients can reach their storage shares over SFTP from outside our network. NFS stays
private to the client's own private network; SFTP is the public way in.

## What the client controls

- **Per share:** `sftp_access` is `off` (default), `ro` (read-only) or `rw` (read-write).
- **Per storage service:** up to 16 SFTP users. Each user has:
  - a short name (`^[a-z][a-z0-9_-]{0,31}$`), from which Rackflow builds the login
    `<name>.<service_id>`, for example `backup.65`;
  - SSH public keys (ed25519, ECDSA, or RSA of at least 2048 bits; up to 16 per user);
  - optionally a password (12 to 72 characters, or generated by Rackflow and shown once);
  - optionally a source address allow list (up to 32 IPv4 or IPv6 CIDRs). Empty means any address;
  - an enabled flag.
- A user sees every share of the storage that has SFTP turned on, as `/<share>`, with that
  share's access mode. All users of a storage see the same shares.

Rackflow stores only bcrypt hashes of passwords (`$2b$`, cost 12) and the public keys. The
storage runner only ever receives those hashes and public keys, never a password.

## Endpoint

Each storage node has its own public endpoint: `sftp_enabled`, `sftp_host` (the public name or
address clients connect to) and `sftp_port` (default 2222) on the node. Clients are shown
`sftp -P <port> <login>@<host>` and the host key fingerprint the runner reports, so they can
check it on first connect. Opening the port on the node's public interface (or a NAT rule to
it) is an operations task; Rackflow does not manage it.

## Isolation design

Two designs were considered.

1. **One shared SFTP server with a chroot per user.** One process (for example OpenSSH
   `internal-sftp` or an in-process SFTP library) has every tenant's shares mounted and
   chroots each login into its tenant's directory. It is simple and uses few resources, but
   every tenant's data is reachable by that one process. A path handling bug, a chroot escape
   or a wrong user-to-directory mapping exposes other tenants' data.
2. **A routing front end plus one locked-down SFTP back end per tenant.** The front end only
   speaks SSH: it authenticates the login against the hashes and keys for that username, picks
   the tenant from the username, and pipes the `sftp` subsystem to that tenant's own back end.
   The back end is OpenSSH's `sftp-server` running inside a per-tenant container that has no
   network, a read-only root, no capabilities, runs as uid 65534, and has only that tenant's
   shares bind-mounted. Those shares are kernel CephFS mounts made with the tenant's own cephx
   user `client.rf-t<id>`, whose Ceph capabilities only cover that tenant's subvolumes.

**Chosen: design 2.** A bug in the SFTP file server (the part that parses paths and touches
files) can only reach what is mounted in that tenant's container, and Ceph itself refuses
access to other tenants' subvolumes because the mount uses the tenant's own key. The front end
never opens a file. The remaining shared component is the front end's username-to-tenant
table; it is small, rebuilt from Rackflow's config on every reconcile, and covered by tests.
The costs are one idle container per tenant with SFTP on, kernel CephFS mounts on the node,
and a container restart when the tenant's set of SFTP shares or their modes change (open SFTP
sessions of that tenant drop then).

The NFS side is unchanged: per-tenant network namespace and NFS-Ganesha. SFTP does not enter
the tenant's network namespace, so it never touches the client's private network.

Files written over SFTP are owned by uid/gid 65534, the same as files written by a squashed
root over NFS, and share roots stay mode 1777/0777, so both protocols can read and write the
same files.

## Protection and logging

- Only the `sftp` subsystem is offered: shell, exec, PTY, environment, agent and port
  forwarding requests are refused.
- At most 6 authentication attempts per connection.
- Brute-force protection per source address: after `max_auth_failures` failed connections (a connection that ends without logging in after at least one failed attempt; each connection allows at most 6 attempts) within
  `failure_window_seconds`, the address is refused for `ban_seconds` (defaults 10, 600 and
  900, served by Rackflow). Unknown usernames cost the same bcrypt work as known ones.
- Source allow lists are checked before any key or password.
- Every authentication result and session start and end is logged on the node (journald) with
  login, tenant, source address, method and key fingerprint, never a password. The runner
  reports the latest successful login per user to Rackflow, which shows it to the client.

## Lifecycle

- **Suspend:** the tenant's logins are removed from the front end at once, its open sessions
  are closed, its SFTP container is stopped and its mounts are released. Data is kept.
- **Unsuspend:** SFTP comes back with the same users and keys.
- **Terminate:** as suspend, then the container, mounts and SFTP state are removed. Data is
  destroyed with the rest of the tenant after the grace period.
- **Share deleted or SFTP turned off on a share:** the share leaves the tenant's container.
- **User deleted or disabled:** the login stops working at the next reconcile and its open
  sessions are closed.

## Runner contract (backwards compatible)

All fields below are optional. A runner that does not know them ignores them; a Rackflow that
does not send them leaves SFTP off.

`GET /api/runner/storage/config`, top level:

```json
"sftp": {
  "enabled": true,
  "port": 2222,
  "max_auth_failures": 10,
  "failure_window_seconds": 600,
  "ban_seconds": 900
}
```

Per tenant (`sftp_users` is only sent while the tenant is `active`; the runner also ignores it
otherwise):

```json
"sftp_users": [
  {
    "id": 7,
    "username": "backup.65",
    "public_keys": ["ssh-ed25519 AAAAC3Nz... laptop"],
    "password_hash": "$2b$12$...",
    "allowed_ips": ["203.0.113.0/24"]
  }
]
```

Per share: `"sftp": "off" | "ro" | "rw"` (missing means `off`).

`POST /api/runner/storage/status`, top level:

```json
"sftp": {
  "listening": true,
  "port": 2222,
  "host_key": "ssh-ed25519 AAAA...",
  "host_key_fingerprint": "SHA256:...",
  "error": null
},
"sftp_logins": [{"user_id": 7, "at": "2026-11-18T10:00:00Z", "ip": "203.0.113.5"}]
```

Per tenant: `"sftp": {"state": "ready" | "pending" | "error" | "off", "error": null}`.

`sftp_logins` holds the latest successful login per user since the last report that Rackflow
accepted.
